# Lead Feature Test Documentation

This README provides an overview of the automated tests implemented for the "Lead" feature within the application. These tests aim to ensure the correct functionality of lead-related models, API interactions, and local data persistence.

## Test File Overview

The lead feature is tested across several dedicated test files, focusing on different layers of the application:

### 1. `test/models/lead_model_test.dart`

**Purpose:** This file contains unit tests for the `Lead` and `LeadNote` data models. It verifies their correct instantiation, data mapping, and utility methods.

**Coverage:**
*   **`LeadNote.fromJson` and `LeadNote.toJson`:** Ensures proper conversion between JSON data and `LeadNote` objects, and vice-versa.
*   **`Lead.fromJson` and `Lead.toJson`:** Verifies the correct mapping of JSON data to `Lead` objects and conversion back to JSON, including nested `LeadNote` objects.
*   **Graceful Handling of Missing/Null Fields:** Tests that the `Lead` and `LeadNote` models can handle cases where optional fields are missing or explicitly null in the input JSON without crashing and default to appropriate values.
*   **`LeadNote.plainText`:** Tests the utility getter that extracts plain text content from potentially HTML-formatted notes.

### 2. `test/services/apis/leads/lead_service_test.dart`

**Purpose:** This file focuses on testing the `LeadService`, which is responsible for interacting with the backend API to fetch lead data. It uses mocking to isolate the service logic from actual network calls.

**Coverage:**
*   **`AuthService.getHeaders`:** Verifies that the correct HTTP headers (including authentication cookies) are generated for API requests.
*   **`fetchBrokerLeads` (Success Scenario):** Tests the successful fetching of leads for a specific broker from the API. It ensures that the service correctly processes a successful API response (HTTP 200) and transforms the raw JSON into a list of `Lead` objects.
*   **`fetchBrokerLeads` (API Error Scenario):** Tests the service's behavior when the API returns an error (e.g., HTTP 500). It verifies that appropriate exceptions are thrown, allowing the application to handle API failures gracefully.

**Dependencies:** This test extensively uses `mockito` for creating mock `http.Client` instances and `AuthService` test values to control the test environment. The `lead_sync_test.mocks.dart` file is generated by Mockito based on the mocks defined in this test file.

### 3. `test/services/databases/lead_database_test.dart`

**Purpose:** This file contains tests for the `LeadDatabase` class, which manages the local persistence of lead data using SQLite (via `sqflite_ffi`). These tests use an in-memory database to ensure isolation and speed.

**Coverage:**
*   **`upsertLead`:** Verifies that new lead data can be successfully inserted into the database and that existing lead data can be updated.
*   **`getAllLeads`:** Ensures that all stored lead records can be retrieved correctly from the database.
*   **`getLeadByName`:** Tests the ability to fetch a specific lead record by its unique identifier (`name`). It also checks behavior for non-existent leads.
*   **`deleteLead`:** Verifies the successful removal of individual lead records from the database.
*   **`deleteAllLeads`:** Tests the functionality to clear all lead records from the database.

## What is (Potentially) Not Covered

While the tests described above provide robust coverage for the fundamental aspects of the Lead feature, it's important to note what might fall outside their scope:

*   **User Interface (UI) / Widget Tests:** Tests that simulate user interaction with lead-related UI components (e.g., displaying lead lists, forms for editing leads).
*   **End-to-End (E2E) Integration Tests:** Tests that cover the entire flow from UI interaction through API calls and database operations in a live or near-live environment.
*   **Complex Business Logic:** Any intricate business rules or workflows specific to leads that are not directly tied to the model structure, API communication, or database CRUD operations (e.g., specific lead scoring algorithms, advanced lead assignment logic, validation beyond basic data types).

Further tests in these areas would provide even more comprehensive validation of the Lead feature.
